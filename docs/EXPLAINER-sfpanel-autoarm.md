# Explainer — панель конструктора, которая сама себя закрывала

Небольшая правка с поучительной причиной. Панель блоков в конструкторе
(`#sfPanel`) появлялась не всегда: приложение её открывало, а через полсекунды
она молча закрывалась. При этом режим конструктора оставался включённым —
`current.sfMode === true`, — то есть пользователь оказывался в режиме
редактирования блоков без панели блоков.

Баг нашёлся сам, по ходу проверки работ по производительности: я заметил, что
сторож палитры видит перекрывающую панель то одну, то ни одной. Сначала списал
на свою правку, но прогон на базовом коммите дал ту же картину — значит, дело не
в ней.

Виноваты **две независимые ошибки**, и каждая по отдельности делала защиту от
этого самого бага бесполезной. Что особенно приятно: автор защиту написал, знал
про проблему и описал её в шапке файла — она просто не работала.

---

## Background

### Что такое автовзвод и зачем он нужен

Движок редактирования блоков в design-lab (подсветка, рамки, перетаскивание)
стартует не при входе в режим дизайна, а в момент **первого открытия панели
блоков**. Поэтому патч `design-autoarm.js` нажимает штатную кнопку панели за
пользователя: иначе человек вошёл в режим дизайна, а блоки не реагируют, пока он
сам не откроет панель.

Патч устроен так: по таймеру раз в секунду и по нескольким таймаутам вызывается
`arm()`, которая проверяет условия и один раз посылает клик по кнопке-тогглу.

Ключевое слово — **тоггл**. Кнопка не «открыть панель», а «открыть/закрыть».
Значит, нажимать её можно только убедившись, что панель закрыта. Автор это знал
и написал в шапке файла:

```
   Важно: нажатие ровно ОДНО и только если панель закрыта. Прошлая версия
   открывала и тут же закрывала панель, а проверка режима могла дёргаться —
   получалось мигание.
```

И поставил соответствующую проверку в `arm()`:

```js
function arm() {
  if (done || !inDesign()) return;
  var box = panel();
  if (box && shown(box)) { done = true; return; }   // ← панель уже открыта
  var button = toggle();
  if (!button) return;
  done = true;
  button.dispatchEvent(new MouseEvent('click', { bubbles: true, cancelable: true, view: window }));
}
```

Логика верная. Ошибки — в двух помощниках, `shown()` и `panel()`.

### Как выглядит панель

Два факта из `index.html`, которые понадобятся дальше:

```css
#sfPanel{position:fixed;top:60px;right:10px;bottom:10px;width:302px;z-index:900;
         display:flex;…;transition:transform .22s cubic-bezier(.32,.72,0,1),opacity .22s}
#sfPanel.sf-hidden{transform:translateX(320px);opacity:0;pointer-events:none}
```

Панель **фиксированная**, а закрывается она не исчезновением, а классом
`sf-hidden`: уезжает за край через `transform` и гаснет до нуля прозрачности.
`display` при этом остаётся `flex`, размеры — прежними 302×730.

## Intuition

### Как я искал виновника

`MutationObserver` показал только факт: класс `sf-panel-on` появляется на
`<body>`, а через ~500 мс исчезает.

```
  run0 (промах):
       3987 мс  body.sf-panel-on ДОБАВЛЕН
       4578 мс  body.sf-panel-on СНЯТ
```

Кто снял — из наблюдателя не видно: его колбэк асинхронный, стека вызова в нём
уже нет. Зато состояние панели в момент промаха оказалось говорящим:

```
display=flex  opacity=0  sf-hidden=true  toggle.sf-on=true
```

Сверим с кодом. Функция `hidePanel()` ставит `display:none` и снимает класс
`sf-on` с кнопки-тоггла. Здесь же `display` остался `flex`, а `sf-on` на тоггле
**на месте**. Значит, это не `hidePanel()`. А вот собственный обработчик тоггла
подходит идеально:

```js
t.onclick = function () {
  var hidden = panel.classList.toggle('sf-hidden');
  t.innerHTML = hidden ? '❮' : '❯';
  document.body.classList.toggle('sf-panel-on', !hidden);
};
```

Он ставит `sf-hidden`, снимает `sf-panel-on` и **не трогает** `sf-on`. Отпечаток
совпал: кто-то нажимает тоггл.

Дальше — подменяем то, что нельзя не заметить: программный `.click()`,
`DOMTokenList.prototype.toggle/add/remove` для интересующих классов, и слушаем
события клика в фазе захвата, помечая `isTrusted`. Стек снимаем **в момент
вызова**, пока он ещё есть:

```js
const origToggle = DOMTokenList.prototype.toggle;
DOMTokenList.prototype.toggle = function (name) {
  if (name === 'sf-hidden' || name === 'sf-panel-on') record(name, stackNow());
  return origToggle.apply(this, arguments);
};
```

Ответ пришёл сразу и однозначный:

```
4439 мс  событие click на sfToggle isTrusted=false
        design-autoarm.js:68
4444 мс  classList.toggle(sf-hidden)
        index.html:9618
        design-autoarm.js:68
4444 мс  classList.toggle(sf-panel-on)
        index.html:9620
        design-autoarm.js:68
```

`isTrusted=false` — клик синтетический, его послал автовзвод. То есть патч,
созданный чтобы **открыть** панель, её закрывал.

### Ошибка первая: `offsetParent` у фиксированного элемента

```js
function shown(el) {
  if (!el) return false;
  var rect = el.getBoundingClientRect();
  return rect.width > 40 && rect.height > 40 && el.offsetParent !== null;
}
```

> ⚠️ **`offsetParent` у `position:fixed` — всегда `null`.** По спецификации
> `offsetParent` возвращает `null`, если элемент фиксированный, или у него
> `display:none`, или это сам `<body>`/`<html>`. Проверка `offsetParent !== null`
> — распространённый способ спросить «элемент в потоке и видим?», и для обычных
> элементов он работает. Для фиксированных он отвечает «не видим» **всегда**,
> открыт элемент или нет.

`#sfPanel` фиксированный. Значит `shown()` для него не мог вернуть `true` ни при
каких обстоятельствах, и защита `if (box && shown(box)) return;` не срабатывала
никогда.

### Ошибка вторая: `<body>` притворяется панелью

```js
var PANEL = '#sfPanel,[id*="sfPanel"],[class*="sf-panel"],[id*="blocksPanel"],[class*="blocks-panel"]';

function panel() {
  var list = document.querySelectorAll(PANEL);
  for (var i = 0; i < list.length; i++) {
    if (list[i].id !== 'pvFrame') return list[i];
  }
  return null;
}
```

Селектор намеренно широкий — патч рассчитан на несколько возможных вариантов
разметки. Но `[class*="sf-panel"]` — это подстрочное совпадение, и под него
подходит класс **`sf-panel-on`**, который висит на `<body>`, когда панель
открыта.

А `querySelectorAll` возвращает узлы **в порядке документа**, а не в порядке
селекторов. `<body>` идёт раньше `#sfPanel`. Получается издевательская петля:
как только панель открывалась, `panel()` начинал возвращать `<body>` вместо
панели — и проверялась видимость не того элемента. У `<body>`, кстати,
`offsetParent` тоже `null`.

Две ошибки, и обе ведут к одному ответу: «панель закрыта». Отсюда и клик.

### Почему баг был плавающим

`arm()` вызывается по таймеру раз в секунду и по таймаутам после загрузки кадра,
а `done = true` разрешает ровно одно нажатие. Дальше всё решает, что случится
раньше:

- клик **до** того, как приложение открыло панель → клик её открывает, потом
  `showPanel()` открывает ещё раз → панель открыта, всё хорошо;
- клик **после** → панель закрывается.

Отсюда «два случая из трёх» в одних условиях и ноль из шести в других: стоит
чуть изменить тайминг загрузки, и соотношение меняется. Именно так гонка и
выглядит: не «иногда ломается», а «зависит от того, кто успел первым».

## Code

### `shown()` — смотреть на то, что действительно означает «закрыта»

```js
function shown(el) {
  if (!el || !el.isConnected) return false;
  var cs;
  try { cs = getComputedStyle(el); } catch (e) { return false; }
  if (!cs) return false;
  if (cs.display === 'none' || cs.visibility === 'hidden') return false;
  if (Number(cs.opacity) === 0 && cs.pointerEvents === 'none') return false;
  var rect = el.getBoundingClientRect();
  return rect.width > 40 && rect.height > 40;
}
```

`offsetParent` убран совсем. Вместо него — вычисленный стиль, потому что
закрытая панель остаётся `display:flex` и проверка по одному `display` тоже
ничего бы не дала.

Отдельно стоит объяснить, почему условие закрытости — **конъюнкция**
`opacity === 0 && pointerEvents === 'none'`, а не одна прозрачность. Пока панель
**выезжает**, `opacity` анимируется от нуля, и в первом кадре она ещё ровно
ноль — по одной прозрачности мы получили бы «закрыта» и снова послали бы клик,
просто в более узком окне. А `pointer-events` переключается мгновенно, без
перехода: класс `sf-hidden` снят — значит `auto`. Итого три состояния
различаются верно:

| состояние | `opacity` | `pointer-events` | ответ |
|---|---|---|---|
| открыта | 1 | `auto` | открыта |
| выезжает (первый кадр) | 0 | `auto` | открыта |
| закрыта (`sf-hidden`) | 0 | `none` | закрыта |

> **Куда лучше ошибаться.** Ошибка «панель закрыта, а на самом деле открыта»
> приводит к клику, то есть к самому багу. Ошибка в обратную сторону — всего
> лишь к тому, что автовзвод ничего не сделает, а панель откроет само
> приложение. Поэтому предикат намеренно смещён в сторону ответа «открыта».

### `panel()` — сначала точное совпадение

```js
function panel() {
  var direct = document.getElementById('sfPanel');
  if (direct) return direct;
  var list = document.querySelectorAll(PANEL);
  for (var i = 0; i < list.length; i++) {
    var el = list[i];
    if (el.id === 'pvFrame') continue;
    if (el === document.body || el === document.documentElement) continue;
    return el;
  }
  return null;
}
```

Точное совпадение по `id` — первым, чтобы порядок документа больше ничего не
решал. Широкий селектор остаётся как запас для другой разметки, но `<body>` и
`<html>` из него исключены: контейнер панели — это никогда не они.

### Отладочный крючок

```js
window.__dlAutoArmState = function () {
  var box = panel();
  return {
    done: done,
    inDesign: inDesign(),
    panel: box ? (box.id || box.tagName.toLowerCase()) : null,
    panelShown: shown(box),
    toggle: (function () { var t = toggle(); return t ? (t.id || t.tagName.toLowerCase()) : null; })()
  };
};
```

`shown()` и `panel()` живут внутри IIFE, и проверить их снаружи было нельзя — а
именно их ответы и были неверными. Крючок делает предикат наблюдаемым: тест
может спросить «что ты сейчас думаешь о панели?» в каждом из трёх её состояний.
В репозитории это уже принятый приём — ср. `window.dlPaletteWhere` в стороже
палитры.

### Попутно: устаревшая проверка в `tools/test_ui.js`

```js
/* было */ js: !!window.__dlFixV4,
/* стало */ js: Object.keys(window).some(function (k) { return /^__dlFixV\d+$/.test(k) && window[k]; }),
```

Метку версии в `dl-fix.js` поднимали до `__dlFixV7`, а тест продолжал искать
`__dlFixV4` и падал **всегда**, на всех пяти разрешениях.

Это не косметика. Ложная тревога вредна не сама по себе, а тем, что обесценивает
проверку: в предыдущей работе я случайно отключил `dl-fix.js` целиком (упомянул
имя файла в комментарии `index.html`, а сборщик считает такое упоминание знаком
«патч уже подключён»), и тест это **не заметил** — он и так был красным. Теперь
проверка смотрит на любую версию метки, и `tools/test_ui.js` даёт 53/61 вместо
48/61 без единого изменения в поведении страницы.

## Verification

### Регрессионный тест

`tools/test_sfpanel.js` — 11 проверок. Главное свойство: он **падает на `main`** и
проходит на ветке. Тест, который не умеет поймать баг, ничего не стоит.

На `main`:

```
     run0: панели нет — {"panelOn":false,"sfMode":true,"exists":true,"hidden":true,"opacity":0,"pointer":"none"}
     run1: панели нет — …
     run2: панели нет — …
     run3: панели нет — …
  ✗ панель открыта во всех 4 прогонах — 0 из 4
```

На ветке:

```
── панель не закрывается сама (4 прогонов)
  ✓ панель открыта во всех 4 прогонах — 4 из 4
  ✓ режим конструктора включён
  ✓ панель не помечена классом sf-hidden — false
  ✓ панель полностью видна (opacity 1) — 1

── предикат «панель открыта» по состояниям
  ✓ автовзвод видит именно панель, а не <body> — sfPanel
  ✓ открытая панель считается открытой
  ✓ закрытая панель считается закрытой — {"shown":false,"display":"flex","opacity":0,"pointer":"none"}
  ✓ закрытая панель осталась display:flex (ловушка для проверки по display) — flex
  ✓ выезжающая панель считается открытой — {"shown":true,"opacity":0,"pointer":"auto"}

── автовзвод по-прежнему открывает закрытую панель
  ✓ панель открыта заново после загрузки кадра

11/11 проверок пройдено
```

Три проверки заслуживают отдельного слова.

**«закрытая панель осталась display:flex»** — это не проверка поведения, а
ловушка на будущее. Она фиксирует неочевидный факт: закрытая панель не исчезает
из потока. Если кто-нибудь однажды «упростит» `shown()` до проверки по `display`,
этот тест покажет, почему так нельзя.

**«выезжающая панель считается открытой»** закрепляет именно тот случай, ради
которого в условии стоит `pointer-events` рядом с `opacity`.

**«автовзвод по-прежнему открывает закрытую панель»** — противоположное
направление, и без него правка была бы бессмысленной: предикат, всегда
отвечающий «открыта», тоже убрал бы лишний клик, но заодно сломал бы смысл
патча. Тест закрывает панель, имитирует загрузку сайта в кадре (это сбрасывает
однократность) и убеждается, что панель открылась заново.

собранную страницу в `_index_cache` и не перечитывает файлы, поэтому после

### Ручная проверка

1. Поднять бэкенд из корня репозитория:
   `AUTH_ENABLED=0 python3 -m uvicorn design-lab.backend.main:app --port 8899`.
2. Открыть `http://127.0.0.1:8899/index.html` → «Создать с нуля».
3. Панель блоков справа должна появиться и **остаться**. До правки она в части
   случаев уезжала за правый край через полсекунды после появления.
4. В консоли `__dlAutoArmState()` — ожидается
   `{done: true, inDesign: true, panel: "sfPanel", panelShown: true, toggle: "sfToggle"}`.
   Главное здесь `panelShown: true`; до правки он был `false` при открытой панели.
5. Свернуть панель кнопкой «❯» — она должна закрыться и **не открываться сама**
   обратно. Ручное закрытие уважается до следующей загрузки сайта в кадре.
6. Перезагрузить превью (например, отправив правку в чат) — панель открывается
   снова, движок блоков работает: рамки и перетаскивание на месте.
7. Повторить пункты 2–3 несколько раз: баг был плавающим, единичный успешный
   заход ничего не доказывает. Автоматически это делает
   `RUNS=8 node tools/test_sfpanel.js`.

## Alternatives

### А. Заменить тоггл на явное «открыть»

Вместо клика по кнопке-переключателю вызывать напрямую то, что открывает панель:
`window.__sfOpenBlocks()` уже экспортирован и внутри зовёт `showPanel()`.

| Плюсы | Минусы |
|---|---|
| Операция идемпотентна: «открыть» дважды — всё равно открыто | Привязывает патч к внутреннему API приложения, которого он сейчас не знает |
| Не нужен предикат «открыта ли панель» вообще | Перестаёт работать для других вариантов разметки, ради которых и написан широкий селектор |
| Гонка исчезает по построению, а не по проверке | Не решает ту же ошибку `offsetParent` в других местах патча |

Это более радикальное и в каком-то смысле более правильное решение: заменить
переключатель на установку состояния — приём, который убирает целый класс гонок.
Я его не выбрал, потому что `design-autoarm.js` намеренно написан так, чтобы не
знать внутренностей приложения: он ищет кнопку по нескольким селекторам и по
тексту. Смена контракта — отдельное продуктовое решение, и его стоит обсудить с
автором патча, а не протаскивать внутри исправления гонки.

### Б. Проверять не видимость, а собственное состояние

Завести в патче флаг «я уже нажимал» и никогда не нажимать второй раз, не
спрашивая DOM.

| Плюсы | Минусы |
|---|---|
| Совсем нет хрупких проверок вычисленного стиля | Флаг уже есть (`done`), и он не помогает: проблема не в числе нажатий, а в том, что единственное нажатие приходит не вовремя |
| Проще читается | Если панель открыл сам пользователь, патч всё равно нажмёт и закроет её |

Этот вариант не работает, и полезно понять почему: `done` ограничивает
**количество** нажатий, а баг — в **моменте**. Одно нажатие в неудачный момент
закрывает панель ровно так же, как десять. Знать состояние панели всё равно
необходимо.

## Quiz

<details>
<summary>1. Почему проверка <code>el.offsetParent !== null</code> не работала для <code>#sfPanel</code>?</summary>

- **A.** Потому что панель лежит внутри iframe, а у элементов в кадре `offsetParent` недоступен.
- **B.** Потому что у элементов с `position: fixed` `offsetParent` по спецификации всегда `null` — независимо от того, видны они или нет. ✅
- **C.** Потому что `offsetParent` работает только после полной загрузки страницы.
- **D.** Потому что панель создаётся динамически и ещё не была в потоке.

**B** — верно. `offsetParent` возвращает `null` для фиксированных элементов, а
также для `display:none` и для самих `<body>`/`<html>`. Для обычных элементов
проверка сработала бы, а `#sfPanel` объявлен как
`position:fixed;top:60px;right:10px`, поэтому ответ «не видим» приходил всегда.

**A** неверно: панель в родительском документе, а не в кадре. **C** неверно:
момент загрузки тут не при чём, баг воспроизводился и через шесть секунд после
открытия. **D** неверно: панель была создана, с размерами 302×730.
</details>

<details>
<summary>2. Каким образом <code>&lt;body&gt;</code> попадал в результат функции <code>panel()</code>?</summary>

- **A.** `document.querySelectorAll` всегда включает `<body>` в результат.
- **B.** Селектор `[class*="sf-panel"]` — подстрочное совпадение, и под него подходит класс `sf-panel-on`, который висит на `<body>` при открытой панели; в порядке документа `body` идёт раньше панели. ✅
- **C.** У `<body>` был установлен атрибут `id="sfPanel"`.
- **D.** Потому что панель является дочерним элементом `<body>`.

**B** — верно. Двойная неприятность: во-первых, `*=` ловит `sf-panel-on` как
подстроку `sf-panel`; во-вторых, `querySelectorAll` сортирует результат по
порядку документа, а не по порядку селекторов в списке, поэтому `<body>`
оказывался первым. Получалась петля: панель открылась → на `body` появился класс
→ `panel()` стал возвращать `body`.

**A** неверно: `<body>` попадает только если подходит под селектор. **C**
неверно. **D** неверно: родство тут ни при чём, важно совпадение с селектором.
</details>

<details>
<summary>3. Почему «закрыта» определяется как <code>opacity === 0 <b>и</b> pointer-events === 'none'</code>, а не по одной прозрачности?</summary>

- **A.** Потому что `opacity` нельзя прочитать из вычисленного стиля во время анимации.
- **B.** Потому что при выезде панели `opacity` анимируется от нуля и в первом кадре равна нулю, а `pointer-events` переключается мгновенно, без перехода — и только он надёжно отличает «выезжает» от «закрыта». ✅
- **C.** Потому что `opacity: 0` не скрывает элемент от мыши.
- **D.** Потому что так требует спецификация `transition`.

**B** — верно. `transition` в `#sfPanel` объявлен для `transform` и `opacity`, а
`pointer-events` в него не входит и меняется сразу вместе с классом. Поэтому в
первом кадре открытия прозрачность ещё нулевая, но `pointer-events` уже `auto` —
и конъюнкция даёт верный ответ «открыта».

**A** неверно: читается нормально, просто значение в этот момент нулевое. **C**
— само по себе верное утверждение, но это не причина выбора; причина в разной
скорости изменения двух свойств. **D** неверно, спецификация этого не требует.
</details>

<details>
<summary>4. Баг воспроизводился то в двух случаях из трёх, то ни в одном из шести. Что определяло исход?</summary>

- **A.** Скорость сети при загрузке шаблона.
- **B.** Успел ли единственный синтетический клик прийти до того, как панель открыло само приложение, или после. ✅
- **C.** Количество вызовов `arm()`: чем больше, тем вероятнее баг.
- **D.** Разрешение экрана: на узких окнах панель не открывалась вовсе.

**B** — верно. Флаг `done` разрешает ровно одно нажатие. Придёт оно раньше
`showPanel()` — панель откроется (и приложение откроет её ещё раз, что
безвредно). Придёт позже — тоггл её закроет. Любое изменение тайминга загрузки
меняет соотношение исходов, что и делало баг «плавающим».

**A** влияет лишь косвенно, через тайминг, и не является механизмом. **C**
неверно: число вызовов ограничено флагом `done`, важен момент единственного
нажатия. **D** неверно, от размера окна поведение не зависело.
</details>

<details>
<summary>5. Зачем в тест добавлена проверка «автовзвод по-прежнему открывает закрытую панель», если баг был в лишнем нажатии?</summary>

- **A.** Для покрытия строк кода в отчёте.
- **B.** Потому что убрать лишнее нажатие можно и «сломав» предикат в другую сторону: если бы `shown()` всегда отвечал «открыта», баг исчез бы вместе со смыслом патча. ✅
- **C.** Чтобы проверить, что `done` сбрасывается по таймеру.
- **D.** Она дублирует первую группу проверок и добавлена на всякий случай.

**B** — верно. Правка сместила предикат в сторону ответа «открыта» осознанно, и
у этого смещения есть цена: перестарайся — и автовзвод не откроет панель тогда,
когда должен, а движок редактирования блоков не запустится. Проверка закрывает
именно это: закрывает панель, имитирует загрузку сайта в кадре и убеждается, что
панель открылась заново.

**A** — не цель. **C** неверно: `done` сбрасывается по событию `load` кадра, а не
по таймеру, и проверяется это лишь попутно. **D** неверно: первая группа
проверяет обратное утверждение — что панель не закрывается сама.
</details>
